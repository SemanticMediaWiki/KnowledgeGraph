# Changelog

All notable changes to this project will be documented in this file.
This project adheres to [Semantic Versioning](https://semver.org/) and
[Keep a Changelog](https://keepachangelog.com/en/1.1.0/).

## [Unreleased]

### Added
- Article/page nodes now show the page's MediaWiki `{{DISPLAYTITLE:...}}` value as their vis-network label when one is set, instead of always showing the raw page title; `KnowledgeGraph::setSemanticDataFromApi()` resolves it server-side via `PageProps::getProperties()` (HTML-stripped, since it renders as a plain-text label) and includes it as a new `displayTitle` field alongside `properties`/`categories` for each title entry, which `addArticleNode()` in `KnowledgeGraph.js` uses in place of the title string when present; the internal node `id` (used for edges/links) is unaffected, only the rendered label changes
- `KnowledgeGraph.js`'s Designer dialog, "By article" tab: the results panel's "Has properties:" list previously only displayed the article's properties as a plain, non-interactive bullet list, with no way to control which properties render as visible on import. It now renders one unchecked `OO.ui.CheckboxInputWidget` per property (via a `FieldsetLayout`, matching the dialog's existing OOUI form controls); every property is still loaded into the graph's underlying node/edge data on "Done" (so nothing has to be re-fetched later), but only the checked properties' nodes/edges start out visible -- unchecked ones are added with `hidden: true` and can be revealed later the same way any other hidden node already can be (e.g. via the existing property legend or by clicking a connected node). The "By properties"/"By categories" tabs are unaffected ([#16](https://github.com/SemanticMediaWiki/KnowledgeGraph/issues/16))
- `property-options?PropertyName#path=value` inline attribute syntax, e.g. `|property-options?Prop_a#color.background=#ccc`: previously the only way to set a single vis-network node option for a property was to author a whole `MediaWiki:...` options page. The part after `#` is now a dot-separated path (via a new `KnowledgeGraph::setNestedValue()` helper) merged into a per-property options array; multiple inline attributes for the same property accumulate (`#color.background=...` and `#color.border=...` both apply), and this must not be confused with a page-based `property-options?Prop_a=MediaWiki:...` reference for the same property — since that resolves to a client-side JS module string (see `getWikipageContent()`) that cannot be merged server-side without executing it, an inline attribute takes precedence and replaces the page-based reference entirely when both are given for the same property ([#99](https://github.com/SemanticMediaWiki/KnowledgeGraph/issues/99))
- `$wgKnowledgeGraphListSeparator` config variable (default `,`): the `nodes=`/`properties=` parser-function parameters were always split on a hard-coded comma via `KnowledgeGraph::applyDefaultParams()`, which incorrectly fragmented page titles or property names that themselves contain a comma (e.g. legal citations, bibliographic entries). The separator is now configurable per wiki, analogous to `$wgPageFormsListSeparator` ([#33](https://github.com/SemanticMediaWiki/KnowledgeGraph/issues/33), [#48](https://github.com/SemanticMediaWiki/KnowledgeGraph/issues/48)). Note: PR [#50](https://github.com/SemanticMediaWiki/KnowledgeGraph/pull/50) proposed a different fix for #48 (reassembling comma-split fragments by probing `Title::isKnown()`), which only papers over the symptom for titles that already exist and doesn't address the underlying hard-coded separator raised in #33; this change addresses the root cause instead.

### Changed
- `KnowledgeGraph.js`'s `attachContextMenuListener()`: a node's right-click property menu previously indicated an already-shown property only via font styling (blue, bold, italic text) on an otherwise identical bullet-point (`● `) entry -- an easily-missed, non-standard signal with no accessible semantics. Each entry now renders a real `<input type="checkbox">` reflecting the property's current visibility (checked = shown), with the click-to-toggle behavior unchanged; the old `.kg-node-properties-menu-property-entry-selected` CSS rule was removed in favor of a small `.kg-node-properties-menu-property-entry-checkbox` layout rule
- `KnowledgeGraphApiLoadNodes`, `KnowledgeGraphApiLoadProperties`, and `KnowledgeGraphApiLoadCategories` (`includes/api/`) shared the same `execute()` shape (init SMW, resolve each requested title/category-member to semantic data via `KnowledgeGraph::setSemanticDataFromApi()`, `json_encode()` the result, `addValue()`) independently in three places — the same structure that had already produced identical copy-paste bugs across two of the three classes (both referencing the undeclared `self::$data` instead of `\KnowledgeGraph::$data`, see #92 above). Extracted the shared shape into a new `KnowledgeGraphApiLoadTrait` (`isWriteMode()`, `mustBePosted()`, `needsToken()`, `execute()`); each class now implements only two small abstract hooks, `getTitlesToLoad()` (which titles/category members to process) and `getPropertiesForTitle()` (which properties to load for a given title), with `KnowledgeGraphApiLoadCategories` also keeping its per-class `buildPropertiesList()` and its running properties accumulator (now an instance property instead of a value threaded through local variables) needed to carry accumulated properties across category members within one request. Purely structural — no externally observable change to any endpoint's response shape ([#93](https://github.com/SemanticMediaWiki/KnowledgeGraph/issues/93))
- `KnowledgeGraph::setSemanticDataFromApi()` no longer reads/writes the public static `KnowledgeGraph::$data` or the private static `KnowledgeGraph::$relationsSeen` as an implicit communication channel with its callers; it now takes `$data`/`$relationsSeen` as by-reference parameters (accumulating across its own recursion) and also returns `$data`, so a call's result is explicit rather than something callers had to read back out of shared static state afterwards. `KnowledgeGraphApiLoadNodes`, `KnowledgeGraphApiLoadProperties`, and `KnowledgeGraphApiLoadCategories` (as well as `KnowledgeGraph::parserFunctionKnowledgeGraph()`) now each thread their own local `$data`/`$relationsSeen` through the call instead of relying on `\KnowledgeGraph::$data`/external reset discipline; this also fixes `KnowledgeGraphApiLoadCategories::execute()`'s pre-existing `self::$data` reference (a class with no such declared property, working only because the read is guarded by `isset()`) and removes the class of fatal ("Access to undeclared static property") this pattern had already caused twice before (see #68, #69 above). The now-unused `KnowledgeGraph::resetSeenRelations()` test-support method (and its dedicated test) was removed, since resetting shared state between calls/tests is no longer necessary ([#92](https://github.com/SemanticMediaWiki/KnowledgeGraph/issues/92))

### Fixed
- `KnowledgeGraph.js`'s `attachContextMenuListener()`: a node's right-click property menu marked a property "selected" (previously shown in blue/bold/italic, now a checked checkbox -- see Changed below) whenever its canonical edge existed in `self.Edges` at all, including edges left `hidden: true`. Since a depth > 1 wizard load (`createNodes()`) pre-creates a hidden edge for *every* reachable property of *every* traversed node -- not just the ones the user actually chose to display -- this made the marker meaningless in practice: every property in the menu showed as "selected" regardless of whether the user had ever picked it. The check now additionally requires the edge to be visible (`!edge.hidden`), matching `hidden: false`'s existing meaning elsewhere as "the user chose to show this."
- Follow-up fixes from a review of the `KnowledgeGraphApiLoadTrait` extraction and `setSemanticDataFromApi()` parameter-threading refactor above: `KnowledgeGraphApiLoadProperties::getPropertiesForTitle()` recomputed `expandInverseProperties()` once per title instead of once per request (now memoized); `KnowledgeGraphApiLoadCategories::getTitlesToLoad()` decoded its `properties` param with unvalidated `json_decode()` and never declared it in `getAllowedParams()` (now split on `|` like the sibling endpoints, and declared); `KnowledgeGraphApiLoadCategories::getPropertiesForTitle()` returned the live, still-growing accumulated-properties list instead of the snapshot for that specific title, making its result depend on the trait's exact call-timing (now captured explicitly per title); `KnowledgeGraphApiLoadTrait::execute()` duplicated the `isset($data[...])` dedup guard already performed by `setSemanticDataFromApi()` (removed); `KnowledgeGraphApiLoadCategories` kept its own `$SMWStore`/`$SMWDataValueFactory` statics duplicating what `KnowledgeGraph::initSMW()` already sets (now resolved directly where used); `setSemanticDataFromApi()` could queue the same linked title for recursion more than once per call when reached via two properties/relations (`$pendingRecursiveTitles` now dedupes itself, not just against `$data`); `applyDefaultParams()` repeated the same filter-then-fallback-to-default logic for `bool`/`number`/`int` (extracted into a shared `validateOrFallback()` helper)
- `KnowledgeGraph::applyDefaultParams()`: for the `number`/`int`/`integer` types, an invalid value (one that fails `filter_var( ..., FILTER_NULL_ON_FAILURE )`) fell through to `settype( null, 'float' | 'integer' )`, which silently produced `0.0`/`0` instead of the type's documented behavior of falling back to the configured default — already the `bool`/`boolean` branch's behavior. Both branches now re-validate `$defaultValue` through the same filter on failure, matching `bool`/`boolean`. Updated `KnowledgeGraphApplyDefaultParamsTest::testNumberInvalidValueBecomesZeroNotDefault()` / `testIntegerInvalidValueBecomesZeroNotDefault()` (which had locked in the old, buggy behavior per #74) to `testNumberInvalidValueFallsBackToDefault()` / `testIntegerInvalidValueFallsBackToDefault()`, asserting the corrected default-fallback behavior. The other silent-fallback call sites reviewed alongside this fix (`getAllPropertiesForNode()`, `setSemanticDataFromApi()`, and the three `KnowledgeGraphApi*` endpoints, which only relay whatever `setSemanticDataFromApi()` returns) were left as `wfDebugLog()`-only intentionally: they exist inside a recursive graph-building traversal where one title/API failure should degrade to a partial graph rather than aborting or exception-ing the whole request ([#95](https://github.com/SemanticMediaWiki/KnowledgeGraph/issues/95))
- `KnowledgeGraphApiLoadNodesExecuteTest::testDepthZeroCreatesRootNodeOnly`, `KnowledgeGraphApiLoadPropertiesExecuteTest::testDepthZeroCreatesRootNodeOnly`, `KnowledgeGraphApiLoadPropertiesExecuteTest::testInversePropsIncludedDoesNotAffectRootNodeCreation`: these three assertions still expected the root-node-only (`depth === 0`) API result shape from before the DISPLAYTITLE feature (`[ 'properties' => [], 'categories' => [] ]`), left stale when that feature added a `displayTitle` key to both branches of `KnowledgeGraph::setSemanticDataFromApi()`'s output but only updated `KnowledgeGraphSetSemanticDataFromApiTest.php` to match — breaking `main`'s CI on every run since. Updated all three to expect `'displayTitle' => null` (no `{{DISPLAYTITLE:...}}` set on the inserted test pages) ([#101](https://github.com/SemanticMediaWiki/KnowledgeGraph/issues/101))
- `KnowledgeGraph.js`'s `attachContextMenuListener()`'s property-click-to-toggle handler: clicking a property in a node's right-click context menu that was already present in the graph (e.g. hidden via the by-article property-visibility selection from #16) did not reliably toggle it, instead sometimes creating a second, parallel node/edge for the same logical value. Root cause: the handler fetched a node's available properties via its own client-side `action=smwbrowse` call and re-derived node/edge ids independently from the server-side logic `KnowledgeGraph::setSemanticDataFromApi()` already uses for the initial graph build -- most notably resolving `_wpg` (wikipage-type) values via the *localized* namespace name (`mw.config.get('wgFormattedNamespaces')`) where the server resolves the same values via the *canonical* (English) namespace name (`NamespaceInfo::getCanonicalName()`), so on a non-English wiki the two code paths computed different ids for the same value (e.g. `Category:Site` vs. `Kategorie:Site`) and the toggle's `self.Edges.get(id)` lookup missed the already-existing edge. Replaced the client-side `smwbrowse` re-derivation with the existing `loadNodes()` helper (the same `action=knowledgegraph-load-nodes` endpoint the initial graph load already uses), so the context menu now renders/toggles using the exact server-canonical property/value shape and ids `createNodes()` was built from; toggling now flips the existing edge's/node's `hidden` flag (matching the visibility model used elsewhere) instead of removing and recreating them. A new `buildNodeAndEdgeFromValue()` helper factors the per-value node/edge-building logic out of `createNodes()` so both call sites stay in sync. Removed `fetchSemanticDataForNode()`, `parseProperties()`, `getPropertyValueForNode()`, `fetchNamespaceNameForNode()`, and `self.nodePropertiesCache`, which existed solely to support the old, independently-re-derived path ([#100](https://github.com/SemanticMediaWiki/KnowledgeGraph/issues/100))
- `KnowledgeGraph.js`'s `attachContextMenuListener()`: the right-click "open article" link entry in a node's context menu always showed the node's raw title text, even for a node labeled with a DISPLAYTITLE-derived display name; it now shows the node's actual rendered label, while the link itself still resolves to the real page title
- `KnowledgeGraph::parserFunctionKnowledgeGraph()`: on a closed wiki (`$wgGroupPermissions['*']['read'] = false`), the ambient user under a maintenance script like `rebuildData.php` is anonymous and lacks the `read` right; the internal `smwbrowse` `ApiMain` call in `setSemanticDataFromApi()` then threw an uncaught `ApiUsageException`, aborting the whole page parse/rebuild. Since this parser function only reads and renders SMW data (it records no page annotations of its own), it now checks `read` permission for the acting user up front and returns an empty string instead of running when that check fails ([#79](https://github.com/SemanticMediaWiki/KnowledgeGraph/issues/79))
- `KnowledgeGraphCanvasPolyfill.js` (new, loaded before vis-network): polyfilled `CanvasRenderingContext2D.prototype.circle`; vis-network's built-in configurator color picker calls this non-standard canvas method directly (unchanged upstream since at least 2021 through the current 10.x release, apparently relying on a legacy jCanvas-style global patch that vis-network never bundles), so opening any `.vis-config-colorBlock` swatch threw `ctx.circle is not a function` and the picker's hue-circle canvas never drew ([#47](https://github.com/SemanticMediaWiki/KnowledgeGraph/issues/47))
- `extension.json`, `package.json`: vendored and registered vis-network's own `vis-network.min.css` alongside the already-vendored `vis-network.min.js`; the built-in "configure" panel (nodes/edges settings opened via the Designer's toolbar) relies on this stylesheet to size its rows, and without it every row — including the `.vis-config-colorBlock` color swatches — collapsed to zero height ([#47](https://github.com/SemanticMediaWiki/KnowledgeGraph/issues/47))
- `KnowledgeGraphToolbar.js`'s and `KnowledgeGraphActionToolbar.js`'s `createTool()`: restored `Tool.prototype.onUpdateState`, which a prior refactor removed as apparently-dead boilerplate; `OO.ui.Tool`'s constructor unconditionally does `this.toolbar.connect(this, { updateState: 'onUpdateState', ... })`, and OOUI's `EventEmitter.connect()` throws unless the named handler is an actual function — `OO.ui.Tool.prototype.onUpdateState` is deliberately `null` (an abstract method subclasses must override), so every `Tool` instantiation on the Designer special page's toolbars threw `Error: Property "onUpdateState" is not a function`, aborting graph/toolbar initialization entirely and leaving the page's config menu (and its color pickers) empty ([#47](https://github.com/SemanticMediaWiki/KnowledgeGraph/issues/47))
- `KnowledgeGraph::parserFunctionKnowledgeGraph()`'s palette-color selection: `$GLOBALS['wgKnowledgeGraphColorPalettes']` was read directly with no config default and no fallback, so a wiki that never explicitly set `$wgKnowledgeGraphColorPalettes` in `LocalSettings.php` raised a PHP "Undefined global variable" error on every `#knowledgegraph` call. Declared `KnowledgeGraphColorPalettes` in `extension.json`'s `config` section (a 10-color qualitative default, matching the other declared `KnowledgeGraph*` settings) so a real MediaWiki bootstrap now always populates the global, and added a literal PHP-level fallback (`KnowledgeGraph::DEFAULT_COLOR_PALETTE`) for the case where the global is unset regardless ([#98](https://github.com/SemanticMediaWiki/KnowledgeGraph/issues/98))
- `KnowledgeGraph.js`'s `export-graph` toolbar action: the wikitext snippet copied to the clipboard by the Graph Designer always hardcoded `depth=0`, regardless of the depth actually used to load/expand nodes in the Designer session, so re-inserting the exported snippet silently reverted to depth 0. `loadNodes()` now records the depth of its most recent call in `self.LastDepth`, and the export snippet uses that value (falling back to `self.Config.depth` if no node was loaded yet) instead of the hardcoded `0` ([#97](https://github.com/SemanticMediaWiki/KnowledgeGraph/issues/97))
- `KnowledgeGraph::getLinkFormatterInfo()`: fixed a Phan `PhanTypeMismatchProperty` finding (breaking the coverage CI job) by narrowing `SMW\DataValueFactory::newDataValueByItem()`'s return type (`DataValue|ErrorValue`) to the concrete `ExternalFormatterUriValue` the code actually relies on via an `instanceof` check before storing it in `self::$externalFormatterValues`, falling back to no external-link formatter (`null`) if SMW ever returns an `ErrorValue` for a malformed `_PEFU` formatter URI instead of storing a value that would later fatal in `formatLinkForValue()`
- `KnowledgeGraphApiLoadCategories::execute()`: fixed a fatal `TypeError` raised whenever the internal `Property:` namespace discovery request failed or returned a non-JSON response; the code issued an outbound, unauthenticated HTTP request to the wiki's own `api.php` (`action=query&list=allpages`) via `HttpRequestFactory`, left the response unguarded, and called `array_column()` on the resulting `null` whenever `json_decode()` failed — on a wiki not reachable from itself over HTTP (e.g. behind a restrictive proxy/firewall) this fataled on every `knowledgegraph-load-categories` request. Replaced the outbound self-call with an in-process `ApiMain` call wrapped in a new `KnowledgeGraph::newDerivativeApiContext()` helper, which preserves the calling user's authenticated session (via `DerivativeContext`) instead of losing it like a bare `FauxRequest` would, and added a defensive fallback for a missing/empty `allpages` result ([#31](https://github.com/SemanticMediaWiki/KnowledgeGraph/issues/31))
- `KnowledgeGraph::getAllPropertiesForNode()`, `KnowledgeGraph::setSemanticDataFromApi()`: closed a latent bug where their internal `smwbrowse` API calls ran in-process via a bare `FauxRequest`/`ApiMain`, which silently lost the calling user's session (`ApiMain` wraps a bare `WebRequest` in a fresh, anonymous `RequestContext`); both now go through `KnowledgeGraph::newDerivativeApiContext()` so permission checks inside the invoked module see the real caller
- `KnowledgeGraph.js`'s `initialize()` `doubleClick` Network handler: it unconditionally opened an article link (`wgArticlePath`) for any double-clicked node, including nodes representing a plain SMW property value (Text, Number, Keyword, URI, Date, Geo, ...) rather than an actual wiki page; it now only opens the article link for a `typeID === 9` (SMW `DataItem::TYPE_WIKIPAGE`) node, matching `attachContextMenuListener()`'s node-link logic, and otherwise opens a configured link formatter (see below) or does nothing ([#49](https://github.com/SemanticMediaWiki/KnowledgeGraph/issues/49))
- `KnowledgeGraph.js`'s `attachContextMenuListener()`: the right-click "🔗" article-link entry used an inverted blacklist check (`nodeTypeId !== 2`, only excluding SMW's Text/BLOB DataItem type) instead of a whitelist; every other non-wikipage value type (Number, Boolean, URI, Time, Geo, Keyword, ...) incorrectly got an article link too. Changed to `nodeTypeId === 9` ([#49](https://github.com/SemanticMediaWiki/KnowledgeGraph/issues/49))
- `KnowledgeGraph.js`'s `createNodes()`: for any property type other than `_wpg`/`_txt`, the per-value `typeID` stored on the node was the raw SMW type-id **string** from the property metadata (e.g. `'_num'`, `'_keyw'`) instead of the numeric SMW `DataItem::TYPE_*` id the API already provides per value (`property.values[i].type`); this made numeric `typeID` comparisons (including the two fixes above) unreliable for nodes created during the initial graph load. Now reads the numeric per-value type directly ([#49](https://github.com/SemanticMediaWiki/KnowledgeGraph/issues/49))
- `KnowledgeGraph.js`'s `initialize()` `doubleClick` Network handler: fixed the node-id-to-article-title extraction to strip a trailing `#typeId` suffix (matching `attachContextMenuListener()`'s convention) instead of splitting on `_` first; a title containing an underscore before a `#typeId` suffix (e.g. `Foo_Bar#9`) previously double-clicked through to `wgArticlePath` with the title truncated to `Foo`, dropping `_Bar` and the suffix entirely and opening the wrong (or a nonexistent) page ([#90](https://github.com/SemanticMediaWiki/KnowledgeGraph/issues/90))
- `KnowledgeGraph.js`'s `addLegendEntry()`: removed a dead `container.innerHTML = id;` statement that ran immediately after `container.innerHTML = label;`, discarding the intended label and always displaying the raw property id on the legend button instead ([#89](https://github.com/SemanticMediaWiki/KnowledgeGraph/issues/89))
- `KnowledgeGraph.js`: fixed a `TypeError: Cannot read properties of undefined (reading 'querySelector')` raised whenever a legend-linked edge was deleted via the edge-deletion-on-click path; that call site invoked `removeLegendEntry( edgePropKey )` as a bare function instead of `removeLegendEntry.call( self, edgePropKey )` (the calling convention `removeLegendEntry`/`dispatchLegendClickEvent` rely on elsewhere, since both read instance state off `this`), leaving `this` unbound; also aligned `removeLegendEntry()`'s `LegendDiv` guard to read `this.LegendDiv` instead of the closure's `self.LegendDiv`, consistent with the rest of the function ([#89](https://github.com/SemanticMediaWiki/KnowledgeGraph/issues/89))
- `KnowledgeGraph.js`'s `cleanLabel()`: trimmed the label before stripping the leading `-`/trailing parenthetical, not just after; trailing whitespace after a `(...)` suffix (e.g. `'-Label (extra)  '`) previously left the parenthetical un-stripped, since the trailing-parenthetical regex requires the `)` to sit at the very end of the string ([#87](https://github.com/SemanticMediaWiki/KnowledgeGraph/issues/87))
- `KnowledgeGraphFunctions.js`: exported the previously-internal `rgbToHex()` helper from the module's public API; it was already used internally by `getContrastColor()` but had no way to be tested or reused on its own ([#81](https://github.com/SemanticMediaWiki/KnowledgeGraph/issues/81))

### Added
- `KnowledgeGraph::getLinkFormatterInfo()`/`formatLinkForValue()` (`includes/KnowledgeGraph.php`), `resolveFormattedLink()` (`resources/KnowledgeGraph.js`): added link-formatter support for two SMW datatypes whose values previously had no navigable link at all now that the double-click/context-menu article link is correctly restricted to wikipage nodes (see above) — a Keyword (`_keyw`) property with a `Formatter schema` (`_FORMAT_SCHEMA`) configured now double-clicks/right-clicks through to a `Special:Ask` query for that keyword value (built client-side, since SMW's own `KeywordValue` link formatter only ever renders a link to `Special:Ask`/`Special:SearchByProperty`, never an arbitrary external URL — see `getLinkFormatterInfo()`'s docblock), and an External Identifier (`_eid`) property with an `External formatter uri` (`_PEFU`) configured now opens the `$1`-substituted external URL, built server-side via SMW's own `ExternalFormatterUriValue::substituteAndFormatUri()` and passed through per value as `formattedUrl` ([#49](https://github.com/SemanticMediaWiki/KnowledgeGraph/issues/49))
- `tests/phpunit/Unit/KnowledgeGraphSetSemanticDataFromApiProcessingTest.php`: added coverage for `getLinkFormatterInfo()`/`formatLinkForValue()` — a plain Number property gets no `linkFormatter`, a Keyword property with/without a configured `Formatter schema` gets `{'kind': 'ask'}`/`null` (and never a server-built `formattedUrl`), and an External Identifier property with/without a configured `External formatter uri` gets `{'kind': 'external'}`/`null` with/without a per-value `formattedUrl` ([#49](https://github.com/SemanticMediaWiki/KnowledgeGraph/issues/49))
